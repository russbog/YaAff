# Фаза 4: Единая токен-система (TokenRegistry)

## Обзор

Фаза 4 вводит единый источник истины для подстановки `{token}`-плейсхолдеров во
всём трекере. До этого резолвинг токенов дублировался: `MacrosProcessor`
подставлял токены в HTML-лендинги и исходящие URL, а Conversion API
(`ConversionApiSender::buildTokens`) строил собственную плоскую карту токенов.
Эти два механизма понимали немного разные наборы токенов и работали по разным
правилам.

`TokenRegistry` объединяет всё это: каждый слой — лендинги, URL-макросы, S2S
постбэки и Conversion API — теперь резолвит одни и те же имена токенов одинаково,
из одного контекста клика.

## Архитектура

```
              ┌──────────────────────────────┐
              │        TokenRegistry          │
              │  resolve() / render() /        │
              │  toArray()                     │
              └──────────────────────────────┘
                 ▲            ▲            ▲
                 │            │            │
        MacrosProcessor  ConversionApiSender  (будущие слои)
         (лендинги,       (buildTokens →
          URL, S2S)        toArray)
```

- `MacrosProcessor` делегирует резолвинг значений в `TokenRegistry` с ленивым
  загрузчиком из БД (грузит строку клика при первом промахе).
- `ConversionApiSender::buildTokens()` строит реестр из строки клика плюс
  оверрайды конверсии (status/payout/revenue/currency/time + параметры запроса) и
  возвращает `toArray()`.

## Контекст клика

Реестр строится вокруг одного клика:

- **clickid / userid** — токены идентичности.
- **строка клика** — колонки (`ip`, `country`, `os`, `ua`, …) и кастомные
  `params`.
- **оверрайды** — явные токены, которые всегда выигрывают (конверсионные
  `status`, `payout`, `revenue`, `currency`, `time`, параметры запроса вроде
  `tid`).
- **loader** (опц.) — колбэк, лениво загружающий строку клика из БД, когда
  колонка/параметр запрошены, но ещё не присутствуют.

## Справочник токенов

| Токен | Источник |
|-------|----------|
| `{clickid}`, `{userid}` | идентичность клика |
| `{domain}` | `HTTP_HOST` |
| `{time}` | текущее unix-время |
| `{px}` | cookie `px` |
| `{ip}` `{country}` `{region}` `{city}` `{lang}` `{os}` `{osver}` `{client}` `{clientver}` `{device}` `{brand}` `{model}` `{isp}` `{connection_type}` `{ua}` `{status}` | колонки клика |
| `{c.NAME}` | кастомный параметр клика `NAME` |
| `{_NAME}` | принудительно кастомный параметр `NAME` из входящей ссылки, минуя встроенные токены (например `{_domain}` берёт `?domain=...`, а не хост редиректа) |
| `{*NAME}` | в `renderUrl()` подставляет значение литерально, без URL-кодирования (например `{*_domain}` сохраняет `/`); можно совмещать с `_`. Обычный `{NAME}` кодируется как раньше |
| `{sub1}` … `{subN}`, `{sub_id_N}` | параметр клика с тем же именем (стиль Keitaro) |
| `{hash:TOKEN}` | md5 от значения другого токена |
| `{random:A-B}` | случайное целое в `[A, B]` |

Оверрайды конверсии также дают `{status}`, `{payout}`, `{revenue}`,
`{currency}`, `{time}` и любые параметры запроса (например `{tid}`) — они
выигрывают над данными клика с тем же именем.

## API

```php
$r = new TokenRegistry($clickid, $userid, $clickRow, $overrides, $loader);
$r = TokenRegistry::fromClick($clickRow, $overrides);   // путь Conversion API
$r2 = $r->withOverrides(['status' => 'Purchase']);      // копия + слияние

$r->resolve('country');          // ?string — null если неизвестно/пусто
$r->render('id={clickid}&g={country}');  // инлайн-подстановка, неизвестное не трогает
$r->toArray();                   // плоская карта {token}=>value для шаблонов
```

Порядок резолвинга: **оверрайды → принудительные параметры (`_NAME`) →
динамические токены (clickid/userid/domain/time/px/hash/random) → кастомные
параметры (`c.*`, `subN`) → колонки клика**.
Неизвестные токены резолвятся в `null` (и не трогаются `render()`).

## Токены в лендингах

`MacrosProcessor::replace_html_macros()` сохраняет обратно совместимую обработку
`{clickid}`, `{userid}` и `{px}` (заменяются пустой строкой при отсутствии), а
затем дополнительно рендерит полный набор токенов через реестр. Лендинги теперь
могут использовать любой токен (например `{country}`, `{c.fbclid}`). Неизвестные
плейсхолдеры не трогаются, поэтому существующая разметка лендингов не страдает.

## Обратная совместимость

- Публичные методы `MacrosProcessor` (`replace_html_macros`, `replace_url_macros`)
  сохраняют сигнатуры и семантику подстановки.
- `ConversionApiSender::buildTokens()` возвращает карту той же формы, что и
  раньше (проверяется существующими тестами Conversion API).
- URL-макросы по-прежнему подставляют только те значения query, которые в
  точности равны `{macro}`; нерезолвленные макросы остаются на месте и логируются.

## Тесты

`tests/TokenRegistryTest.php` покрывает резолвинг (идентичность, колонки,
кастомные параметры, sub-токены, оверрайды, hash, random), `render()`
(подстановка, сохранение неизвестного, короткие замыкания), `toArray()`,
`withOverrides()` и ленивую загрузку.
