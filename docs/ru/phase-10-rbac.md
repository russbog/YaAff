# Фаза 10: Мультипользовательский режим и ролевая модель (RBAC)

Фаза 10 превращает единый общий пароль админки в многопользовательскую систему
с ролями и точечными правами — не ломая существующие установки. Пока не создан
первый пользователь, трекер сохраняет прежний вход по одному паролю и считает
вошедшего администратора супер-админом.

## Понятия

- **Право (permission)** — строка с пространством имён через точку
  `"{type}.{action}"`, например `offers.view`, `offers.manage`, `users.manage`.
  Права — это чистые данные; роль — просто их список. Маски:
  - `*` — всё (супер-админ)
  - `offers.*` — любые действия в пространстве `offers`
  - `*.view` — действие `view` во всех пространствах
- **Роль (role)** (таблица `roles`) — именованный, управляемый данными набор
  прав. Полноценная сущность, как и остальные (Networks, Offers, ...). Добавить
  право — значит отредактировать список, а не код.
- **Пользователь (user)** (таблица `users`) — учётная запись. Логин — это поле
  `name` сущности; всё остальное лежит в бессхемном `settings`:
  - `password` — bcrypt-хэш (`password_hash`); открытый пароль никогда не
    попадает в БД и не возвращается в UI.
  - `role` — ссылка на роль (id или имя), разрешается в права при входе.
  - `enabled` — общий выключатель (по умолчанию включён).
  - `api_token` — bearer-токен для REST API (используется в Фазе 11).
  - `permissions` — необязательные дополнительные права поверх ролевых.
- **Эффективные права** = права роли ∪ доп. права пользователя.
- **Встроенная роль `admin`** — имя `admin` всегда даёт `*`, даже если строки
  роли нет, поэтому самый первый пользователь всегда работоспособен.

## Архитектура (разделение ответственности)

- `auth/AccessControl.php` — **чистая** логика разрешения прав (сопоставление
  масок). Без I/O, полностью покрыта юнит-тестами.
- `auth/Authenticator.php` — **резолвер на основе БД**, без сессий. Получая
  `DbDriver`, проверяет учётные данные/токены и формирует неизменяемый контекст
  сессии `{id, name, role, permissions}`. Тестируется с любым драйвером.
- `auth/Auth.php` — **слой сессии/HTTP** (обычные функции). Единственное место,
  работающее с `$_SESSION` и отдающее HTTP-ответы:
  - `auth_multiuser()` — есть ли хотя бы одна учётная запись?
  - `auth_current_user()` — контекст из сессии или `null` (legacy-режим).
  - `auth_attempt($user, $pass)` — проверить и начать сессию.
  - `auth_can($permission)` — булева проверка (в legacy-режиме всегда true).
  - `auth_require($permission, $json=false)` — проверить либо вернуть `403`.

## Обратная совместимость

`auth_can()` / `auth_require()` — **no-op, пока нет учётных записей**, поэтому
все страницы и эндпоинты Фаз 0–9 продолжают работать без изменений. Как только
создан первый пользователь, `auth_multiuser()` становится истиной и:

- форма входа требует имя пользователя (проверка по таблице `users`), и
- проверки прав начинают применяться везде.

Вход по старому `adminPassword` работает только пока пользователей ноль.

## Точки контроля доступа

- **Generic entity API** (`admin/entityapi.php`) — перед каждым действием:
  `view`-действия требуют `"{type}.view"`, изменения (`save`/`delete`) —
  `"{type}.manage"`. Поля-пароли хэшируются при сохранении и **скрываются**
  (показываются как `********`) в ответах `list`/`get`.
- **Generic entity pages** (`admin/entitypage.php`) — закрыты
  `auth_require("{type}.view")`.
- **Навигация** (`admin/header.php`) — у каждого пункта меню есть требуемое
  право; недоступные пункты скрываются.

## Преднастроенные роли

Миграция `014_create_roles.php` создаёт три стартовые роли:

| Роль    | Права                                        |
|---------|----------------------------------------------|
| Admin   | `*`                                          |
| Manager | управление кампаниями/офферами/лендингами/...|
| Analyst | `*.view`, `reports.view`, `conversions.view` |

Миграция `015_create_users.php` создаёт таблицу `users` **без сидов** — именно
пустая таблица сохраняет активным режим единого пароля.

## Админка

Откройте **Users** и **Roles** в меню (видны пользователям с соответствующим
правом). Обе страницы — тонкие обёртки над generic-админкой, управляются
схемами `users` / `roles` в `admin/entityschemas.php`:

1. Создайте **Роль** с нужными правами.
2. Создайте **Пользователя**, задайте пароль, выберите роль, оставьте *enabled*.
3. С этого момента вход требует имя+пароль, а меню/API применяют права.

Чтобы сменить пароль, отредактируйте пользователя и введите новый; пустое поле
пароля сохраняет прежний хэш.
